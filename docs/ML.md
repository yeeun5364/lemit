## 1. 무엇을 하는가

강사와 수강생이 LEMIT 안에서 메일처럼 메시지를 주고받습니다. **수강생이 보낸 메시지**는 직접 학습시킨 모델이 네 가지 중 하나로 분류하고, 강사 메시지함에 배지로 보여줍니다. 강사가 쓴 답장은 분류하지 않습니다. 모델이 수강생·학부모 말투로 학습되었기 때문입니다.

| 분류 | 화면 표시 | 기준 (라벨링 가이드) |
|---|---|---|
| `CANCELLATION` | 휴강 요청 | 수업을 쉬겠다는 내용. 대신할 날짜·추가 수업 제안이 **없음** |
| `MAKEUP` | 보강 요청 | 빠졌거나 빠질 수업을 **다른 날 추가로** 하자는 내용. "못 가니 금요일에 보강"처럼 휴강+보강이 함께 있으면 `MAKEUP` |
| `RESCHEDULE` | 일정 변경 | **같은 회차**의 날짜·시간·장소·방식(온라인 등)을 옮기는 내용 |
| `GENERAL` | 일반 메시지 | 인사·감사, 숙제·교재·준비물 문의, 결제·영수증, 진도·상담 등 일정 요청이 아닌 것 |

**원칙: 예측은 참고용입니다.** 예측 결과로 회차 상태나 일정을 자동으로 바꾸지 않습니다. 강사가 배지를 보고 일정 추가·수정 등을 직접 합니다.

- **v2 (2026-11-19):** 수강생이 강사에게 보내는 메시지를 분류하는 방향으로 바꿨습니다.
  - 학습·검증·추론 코드는 그대로 재사용했습니다.

## 2. 기술 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| 모델 | TF-IDF + Logistic Regression (scikit-learn) | 데이터가 수백 건이라 딥러닝보다 단순 선형 모델이 과적합이 적습니다. 학습 약 1초, 추론은 분류 1건 약 1.0~1.6ms(운영 서버, 모델 캐시 사용, §6 측정)이고 CPU만으로 동작해 GPU나 별도 추론 서버가 필요 없습니다. |
| 특징 | 글자 단위 n-gram(`char_wb`, 1~3) | 한국어는 조사·어미가 붙어 띄어쓰기 단위 단어 형태가 계속 바뀝니다("보강", "보강해", "보강은"). 글자 단위로 자르면 형태소 분석기(KoNLPy, Java 필요) 없이도 이 문제가 줄어듭니다. 교차검증에서 단어 단위보다 macro F1이 약 0.07 높았습니다(v2 기준). |
| 저장 | joblib + 메타데이터 JSON | scikit-learn의 기본 저장 방식입니다. 버전·해시·점수를 JSON에 함께 기록해 두고 불러올 때 확인합니다. |
| 서비스 구조 | Django 모놀리스 안에서 직접 추론 | 모델 파일이 70KB이고 추론이 가볍습니다. FastAPI 같은 별도 서버를 두면 배포할 것과 장애 지점만 늘어납니다(기획서 §7 모놀리스 원칙). |
| 외부 AI API | 사용 안 함 | 과제 조건이 "직접 학습한 모델"입니다. 또 메시지를 외부로 보내지 않아도 됩니다. |

### 발표 질문: 왜 로지스틱 회귀를 썼나요?

처음에는 직접 작성한 합성 예문 311건으로 수강생 메시지를 네 가지 유형으로 분류하고, 기존 Django 서버에서 CPU만으로 추론할 수 있는 단순한 선형 모델이 필요해 로지스틱 회귀를 선택했습니다. 메시지함은 모델이 계산한 가장 높은 분류 확률이 50% 미만이면 ‘확신 낮음’을 표시합니다. 로지스틱 회귀는 이 값을 `predict_proba()`로 바로 제공합니다.

이후 로컬 Docker에서 같은 데이터 분할(학습 248건·검증 63건)과 문자 단위 TF-IDF(1~3그램)를 사용해 분류 알고리즘을 추가로 비교했습니다. 각 모델의 설정은 학습 데이터 안에서 5겹 교차검증으로 골랐습니다.

| 분류 모델 | 교차검증 macro F1 | 검증 macro F1 | 메시지 1건 예측 |
|---|---:|---:|---:|
| 로지스틱 회귀 | 0.9471 | 0.9357 | 0.80ms |
| 다항 나이브 베이즈 | 0.8871 | 0.9163 | 0.56ms |
| 선형 SVM (`LinearSVC`) | 0.9475 | 0.9365 | 0.50ms |

예측 시간은 메모리에 올라간 모델이 TF-IDF 변환부터 최종 분류까지 처리하는 데 걸린 시간입니다. 확률 계산은 측정 범위에서 제외했습니다. TF-IDF와 분류기를 함께 저장한 압축 `joblib` 파일은 로지스틱 회귀 67,965바이트, 선형 SVM 65,777바이트였습니다. 두 모델은 합성 검증 데이터에서 분류 성능과 파일 크기가 비슷했습니다. 비교에 사용한 `LinearSVC`의 점수를 현재 화면의 확률 기준에 적용하려면 별도 확률 보정이 필요합니다.

> “예문이 311건이었고, 기존 웹 서버에서 바로 분류할 수 있는 가벼운 모델이 필요해서 로지스틱 회귀를 골랐습니다. 이후 선형 SVM과도 비교해 보니 분류 성능과 파일 크기는 비슷했습니다. 로지스틱 회귀는 분류 확률을 바로 계산해 주기 때문에, 저희는 그 값으로 판단이 어려운 메시지에 ‘확신 낮음’을 표시하고 있습니다.”

## 4. 학습과 평가 절차 (`python -m ml.train --version v2`)

1. 데이터를 확인합니다: 분류 이름, 빈 문장, 중복, 확인용과의 겹침, 클래스별 개수.
2. 학습 80%와 검증 20%로 층화 분리합니다(시드 42).
3. 학습 80% 안에서 5겹 교차검증으로 후보 8개를 비교합니다(글자/단어 단위, n-gram 범위, 규제 C). TF-IDF가 Pipeline 안에 있어서 접힘마다 학습 부분에만 맞춰지므로, 검증 데이터가 학습에 새지 않습니다.
4. 고른 모델을 검증 20%로 평가합니다. 정확도, 정밀도, 재현율, F1, 혼동행렬, 오분류 목록을 봅니다.
5. **성능 기준(학습 전에 정함): 검증 macro F1 ≥ 0.80.** 넘을 때만 저장합니다. 확인용 60건도 같은 지표로 계산해 기록하지만 기준에는 쓰지 않습니다 (PR #34 리뷰 반영).
6. 다음 세 파일을 저장합니다.
   - `ml/artifacts/message_classifier.joblib`: 전처리와 모델을 묶은 Pipeline
   - `message_classifier.json`: 버전, 학습 시각, Python·scikit-learn·numpy 버전, 모델 해시, 데이터 해시, 점수, 검증 문장
   - `REPORT.md`: 사람이 읽는 학습 결과

저장하는 모델은 학습 80%로만 학습한 것입니다. 전체 데이터로 다시 학습하면 조금 나아질 수 있습니다. 하지만 그러면 기록된 검증 점수가 저장된 모델의 점수가 아니게 되고, CI에서 그 점수를 재현할 수 없어서 이렇게 정했습니다.

### 한계

- **데이터가 적습니다.** 311건을 한 사람이 썼습니다. 실제 메시지는 더 길고, 오타와 이모티콘이 많고, 요청 여러 개가 섞여 있습니다. 그런 메시지에서는 점수가 더 낮을 것으로 예상하지만, 실제 데이터로는 검증하지 못했습니다.
- 모델이 핵심 단어("보강", "취소", "옮기", "가능할까요")에 크게 의존합니다. 그래서 돌려 말하는 표현이나 부정문("보강은 안 해도 돼요")에 약합니다.
- 메시지 하나는 분류 하나로만 나옵니다. "휴강하고 다음 주에 보강"처럼 요청이 섞여 있으면 둘 중 하나만 표시됩니다.
- 화면에서는 가장 높은 확률이 0.5 미만이면 "확신 낮음"을 함께 표시해, 강사가 결과를 그대로 믿지 않도록 합니다.

## 5. 웹서비스 연동

### 구현했고 테스트를 통과한 부분

- **`inbox/classifier.py`**
  - `classify(text)`는 분류, 확신도, 모델 버전을 돌려줍니다.
  - 빈 메시지는 `ValueError`를 냅니다. 500자를 넘으면 앞 500자만 씁니다.
  - 모델에 문제가 있으면 `MessageClassifierUnavailable`을 냅니다.
  - **캐시 정책:** 불러오기에 성공한 모델은 프로세스가 끝날 때까지 재사용합니다. 그래서 같은 경로의 파일을 바꿔도 실행 중인 서버는 이전 모델을 씁니다. **모델 교체는 새 이미지 배포(프로세스 재시작)로만 합니다.** 불러오기 실패는 캐시하지 않으므로, 파일 누락·손상을 고치면 재시작 없이 다음 요청부터 동작합니다. 두 동작 모두 테스트로 확인합니다.
- **`ml/artifact.py`의 `load()`** 는 다음 네 가지를 확인하고, 하나라도 어긋나면 모델을 쓰지 않습니다.
  - 파일이 있는지
  - SHA-256 해시가 맞는지
  - scikit-learn 버전이 같은지
  - 분류 목록이 같은지
- **`/healthz/`** (GET, 로그인 불필요)
  - DB 연결이 실패하면 503을 돌려줍니다.
  - 모델을 쓸 수 없으면 200을 돌려주되 `message_classifier.status`를 `unavailable`로 표시합니다. 모델은 부가 기능이라, 없어도 일정 관리는 계속 동작해야 하기 때문입니다.

- **외부 API `POST /api/v1/messages/classify/`** (#101, 2026-11-25, 로컬 테스트 통과)
  - `classify()`를 그대로 호출해 웹과 같은 기준을 씁니다. 이를 위해 `MessagePrediction`에 `scores`(분류별 확률 전체)와 `truncated`(500자 초과 여부)를 추가했습니다. 기존 웹 동작은 바뀌지 않습니다.
  - 모델을 쓸 수 없으면 503 `model_unavailable`(`retryable: true`)로 답하고, 원인은 서버 로그에만 남깁니다.
  - 사용법과 curl 예시는 [API.md](API.md)에 있습니다.

### 설계: 메시지함 (UC-17, A안)

**수강생 계정은 만들지 않습니다.** 발표 MVP에서는 강사가 "수강생 메시지 추가"로 가상 수강생 메시지를 등록합니다(A안). 데모 데이터 명령(#24)에도 미리 넣어 둡니다.

데이터 구조는 양방향을 전제로 설계합니다. 그래서 나중에 수강생 전용 링크(B안)나 수강생 계정(C안)을 붙여도 구조를 바꿀 필요가 없습니다.

| 모델 | 필드 |
|---|---|
| `Conversation` (대화 스레드) | `teacher`(FK User), `student`(FK Student, PROTECT), `subject`, `last_message_at`, `created_at` |
| `Message` (메시지 1건) | `conversation`(FK, CASCADE), `sender`(`student`/`teacher`), `body`(최대 1000자), `sent_at`, `read_at`(null이면 안 읽음), `predicted_label`, `confidence`, `model_version`, `classified_at` |

- 예측 필드는 모두 비워둘 수 있습니다. 강사가 보낸 메시지이거나 모델을 쓸 수 없을 때도 메시지는 저장되어야 하기 때문입니다.
- 상세는 문서 PR에서 [ERD.md](ERD.md)에 추가합니다.

| 화면 | 주소 (안) | 내용 |
|---|---|---|
| 메시지함 | `/inbox/` | 대화 목록: 보낸 사람, 첫 줄, 최근 수강생 메시지의 분류 배지, 시각, 안 읽음 표시. 분류 탭(전체·휴강·보강·일정 변경·일반)으로 필터 |
| 대화 상세 | `/inbox/<id>/` | 메시지를 시간순으로 보여줌(수강생은 왼쪽, 강사는 오른쪽). 수강생 메시지에는 분류 배지. 아래에 답장 입력칸과 [회차 보기]·[일정 추가] 바로가기. 열면 읽음 처리 |
| 수강생 메시지 추가 (시연용) | `/inbox/new/` | 수강생을 고르고 제목과 본문을 입력하면, 수강생이 보낸 메시지로 저장하고 분류 |

- **분류 실패:** 메시지는 저장하고 배지 자리에 "분류 불가"를 표시합니다. 다른 기능에는 영향이 없습니다.
- **권한:**
  - 대화는 `teacher=request.user`로 좁힌 쿼리셋에서 찾습니다. 다른 강사의 대화 주소로 들어오면 404입니다.
  - 수강생 선택지는 로그인한 강사의 수강생으로 제한합니다.
  - 저장 직전 `clean()`에서 `conversation.student.teacher == conversation.teacher`를 다시 확인합니다.
  - 강사 A·B 두 계정으로 격리 테스트를 둡니다.
- **중복 저장 방지:** 저장 후 항상 리다이렉트(PRG)해서, 새로고침해도 메시지가 다시 저장되지 않습니다.
- **일정은 자동으로 바뀌지 않습니다.** 바로가기 버튼은 해당 화면으로 이동만 합니다.

- **모델 파일은 git에 커밋합니다** (70KB). 크기가 작아서 Git LFS나 별도 저장소가 필요 없습니다. `.gitattributes`로 CSV 줄바꿈은 LF로, 모델 파일은 바이너리로 고정합니다.
- **라이브러리 버전을 고정합니다.** `requirements.txt`에 `scikit-learn`, `joblib`, `numpy` 버전을 고정합니다. scikit-learn 버전을 올리면 `ml.verify`가 실패하므로 다시 학습해야 합니다.
- **재학습은 태그 배포 파이프라인에서만, 태그 커밋의 데이터·코드로 합니다 (2026-11-22 변경).** 예전에는 "검토 없이 모델이 바뀌는 것"을 막으려고 CI에서 재학습하지 않았습니다. 지금은 버전 태그를 올릴 때 `2. train`이 **main에 병합된(검토된) 그 커밋의** `ml/data`와 학습 코드로 다시 학습합니다. 그래서 데이터·코드가 PR을 거치지 않으면 모델도 바뀌지 않습니다. 고정 시드·고정 라이브러리라 같은 커밋이면 같은 모델 파일이 나옵니다(로컬 재학습 결과가 커밋된 모델과 SHA-256까지 같음, train 요약의 "커밋된 모델 파일과 같은 바이트"). PR·main push CI는 지금처럼 재학습하지 않고 커밋된 모델을 `ml.verify`로 확인합니다.

### 태그 배포 파이프라인의 학습과 parity (2026-11-22, PR #74로 main 반영)

- **학습(`2. train`):** `python -m ml.train --version <커밋된 모델 버전>+<버전 태그>`(예: `v2+v0.1.2`) → 성능 기준(검증 macro F1 ≥ 0.80, `GATE`)을 넘을 때만 저장 → `python -m ml.verify --model <저장한 파일>` → `python -m ml.parity dump`(학습 환경의 예측 기록). 모델 버전·검증 점수·모델 파일 해시를 작업 출력과 요약에 남기고, 파일은 아티팩트로 다음 작업에 넘깁니다. 이미지에는 이 파일이 들어가고(커밋된 `ml/artifacts` 파일을 덮어씀), `/healthz/`와 분류 결과의 모델 버전이 이 값이 됩니다.
- **기존 기준과의 관계:** 기존 저장소에 parity라는 단계는 없었습니다. 가장 가까운 것은 `ml.verify`의 점수 재현(기록된 macro F1과 다시 계산한 값의 차이 ≤ 1e-4)입니다. 이 확인은 개발 PC(Windows)와 GitHub CI(Ubuntu)에서 통과했습니다. parity는 이 허용 오차를 그대로 쓰고, 예측 하나하나와 확률까지 비교합니다.
- **비교 대상:** 같은 모델 파일(SHA-256 확인)과 같은 입력(메타데이터의 검증 문장 63건 + `ml/data/unseen.csv` 60건, 입력 목록 해시 확인)입니다.
- **비교 항목·허용 오차:**
  - 예측 분류: **전부 같아야 함**(허용 오차 0).
  - 분류별 확률: 최대 차이 ≤ **1e-6**.
  - 검증·확인용 macro F1: 차이 ≤ **1e-4**.
  - 확률에 허용 오차를 두는 이유: 같은 파일이라도 CPU·BLAS·OS에 따라 부동소수 끝자리가 달라질 수 있습니다. 화면에 보이는 확신도는 소수 셋째 자리까지입니다.
- **비교 환경:**
  - `3. parity`: 학습 환경(GitHub-hosted Ubuntu + setup-python) ↔ 서비스 런타임(`Dockerfile`의 `FROM` 이미지 + `requirements.txt`).
  - `4. image`: 학습 환경 ↔ 실제로 게시할 이미지의 컨테이너.
  - 실행 요약에 두 환경의 Python·플랫폼·scikit-learn·numpy·scipy·joblib 버전과 항목별 결과를 표로 남깁니다.
- **로컬 확인 (2026-11-22):** Windows PC에서 학습·기록한 예측을 Linux 컨테이너(Python 3.14.10, scikit-learn 1.9.1, numpy 2.5.5)에서 비교했습니다. 결과는 다음과 같습니다.
  - 123건 모두 같은 분류였습니다.
  - 확률 최대 차이는 검증 0, 확인용 3.47e-18이었습니다.
  - macro F1은 0.9357 / 0.9833으로 같았습니다.
  - 일부러 바꾼 기록(분류 1건, 확률 +2e-6, F1 +0.001, 모델 해시, 입력 해시)은 모두 실패로 잡았습니다(`ml/test_parity.py`).
- **parity가 실패하면:** 배포하지 않습니다. 대부분 학습 환경과 서비스 이미지의 라이브러리 버전이 달라진 경우입니다(`requirements.txt` 고정 확인, 기반 이미지의 Python 버전). 요약 표의 환경 줄을 비교합니다.

### 모델 캐시 효과 측정 (2026-11-20, #51)

`scripts/bench_model_cache.py`로 측정했습니다.
- 두 경우 모두 서비스 경로 그대로 `classifier.classify()`를 재고, 차이는 모델 캐시뿐입니다.
  - 캐시 없음: 측정마다 타이머 밖에서 캐시를 비워 매번 모델 파일을 다시 불러옵니다.
  - 캐시 있음: 프로세스당 한 번만 불러옵니다.
  - 캐시 없음 쪽에는 모델을 불러올 때마다 남는 INFO 로그(`메시지 분류 모델 로드`) 출력 시간도 들어 있습니다. 캐시가 없는 서비스도 같은 로그를 남기므로 서비스 경로 그대로 잰 값입니다. 로그를 뺀 로드 시간은 표의 '모델 로드만' 행입니다.
- 메시지 4종(취소·보강·일정 변경·일반)을 번갈아 분류하고, DB는 읽거나 쓰지 않습니다.
- 운영 서버는 실행 중인 web 컨테이너 안에서 3회 측정했습니다(`docker compose exec -T web python scripts/bench_model_cache.py`).

| 항목 (중앙값) | 운영 서버 (Lightsail 2GB, 3회) | 개발 PC (Windows, 2회) |
|---|---|---|
| 캐시 없음: 매번 모델 로드 (n=50) | **10.2~27.4ms** | 11.0~11.1ms |
| 캐시 있음 (n=500) | **1.0~1.6ms** | 0.5~0.8ms |
| 차이 | **약 10~17배** | 약 14~21배 |
| 모델 로드만 (`artifact.load()`, n=20) | 8.7~32.9ms | 9.9~11.3ms |
| 측정 프로세스의 첫 분류 (모델 첫 로드 포함) | 1,164~1,460ms | 1,904~4,087ms |

- 측정마다 차이가 큽니다. 운영 서버는 CPU를 순간적으로만 높게 쓰는 Lightsail 요금제의 영향으로 추정하며(확인하지 않음), 개발 PC는 다른 작업의 영향을 받습니다. 그래서 하나의 값이 아니라 범위로 적었습니다. 어느 회차에서도 캐시 쪽이 10배 이상 빨랐습니다.
- 분류 시간의 대부분은 **모델 로드 과정**(`artifact.load()`: 파일 읽기, SHA-256 확인, 역직렬화, 버전·분류 목록 검사)이고, 캐시가 이를 없앱니다. 다만 절대 시간은 작아서 사용자가 적은 지금은 체감하기 어렵습니다. 캐시의 의미는 "요청마다 같은 모델을 다시 불러오는 반복 작업을 없앤다"에 있습니다.
- **'첫 분류' 값은 모델을 처음 불러오는 측정 프로세스의 시간입니다.** 실제 사용자의 첫 요청 지연과는 다릅니다.
  - 운영의 gunicorn 작업 프로세스는 `/healthz/`(`classifier.status()`)를 처리할 때 모델을 미리 불러옵니다. 그래서 헬스체크를 이미 처리한 작업 프로세스는 첫 사용자 분류에서 이 비용을 내지 않습니다.
  - 실제 요청 경로의 첫 요청 지연은 측정하지 않았습니다.
- 캐시 범위 결정(모델만 캐시, 수업·회차·메시지 데이터는 캐시하지 않음)은 [PROJECT_PLAN.md](PROJECT_PLAN.md) §7에 있습니다.

## 7. 다시 학습하는 방법

```bash
pip install -r requirements-dev.txt
python -m ml.train --version v3     # 기준 미달이면 저장하지 않고 종료 코드 1
python -m ml.verify                 # 저장된 모델 확인
python manage.py test inbox
```

데이터 변경과 모델 파일 3개(`message_classifier.joblib`, `message_classifier.json`, `REPORT.md`)를 같은 커밋에 넣습니다. 그다음 이 문서의 결과 표와 devlog를 갱신합니다. 확인용 문장의 오분류를 보고 학습 데이터를 고쳤다면, 확인용 문장도 새로 작성해야 "처음 보는 문장"으로 평가하는 의미가 유지됩니다.
