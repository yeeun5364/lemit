## 1. 상태와 우선순위 구분

- **기존 확정 방향:** Python 3.14 · Django 5.2 LTS · PostgreSQL 18 · Docker Compose · GitHub Actions · AWS Lightsail. 개인 개발의 단일 서버 모놀리스 방식. 자세한 작업 수용 기준은 기존 이슈 #4~#7을 따른다.
- **기존 계획(미검증):** web(Django/Gunicorn/WhiteNoise) + db(PostgreSQL/영속 볼륨) 2개 컨테이너, `/healthz/`, `pg_isready`, PR 테스트, 커밋 해시 이미지 버전, 스모크 테스트, 이전 이미지 롤백.
- **신규 권고(미확정):** 아래의 HTTPS 경계, 백업 주기·보관 기간, 알림 임계값, 복구 목표, 비밀정보·데이터 운영 정책. 운영자 확인 후 수치와 구현 방식을 확정한다.
- 완료 표시는 체크리스트와 실제 검증 결과(실행 날짜, 환경, 명령, 결과/링크)를 남긴 뒤에만 바꾼다. 문서를 만들었다는 이유만으로 인프라가 구축된 것으로 표시하지 않는다.

## 2. 구성과 네트워크 경계

```text
인터넷 사용자
  └─ HTTPS :443 (HTTP :80은 HTTPS 리다이렉트 또는 인증서 발급)
       └─ TLS 종료 지점(리버스 프록시: 선정 필요)
            └─ Django / Gunicorn (Docker web, 내부 연결)
                 └─ PostgreSQL (Docker db, 내부 네트워크, 영속 볼륨 pgdata)
외부 관리 접속 ─ SSH 키 인증 + 접속원 IP 제한 (가능하면)
외부 백업 저장소 ← 서버 내 자동 백업 작업 (설계 필요)
```

- 이 구성은 **제안된 운영 아키텍처**다. 기존 #5의 'web+db 2컨테이너' 방침과 양립하도록 TLS 프록시는 호스트 또는 별도 구성으로 결정한다. reverse proxy 도입 여부·제품(Caddy/Nginx 등)은 미확정이다.
- DB의 5432 포트를 인터넷에 공개하지 않는다. Gunicorn도 인터넷에 직접 노출하지 않는다. Docker 포트 바인딩은 내부/loopback 범위로 제한한다.
- 서버 인스턴스 사양·OS·정적 IP·도메인·TLS 인증서 발급/갱신 방식·실제 월 비용은 구축 시 결정하고 근거를 기록한다.
- 서버 관리 접근은 SSH 공개키 방식, 비밀번호 로그인 비활성화를 기본으로 한다. 서버 방화벽과 Lightsail 네트워크 방화벽을 모두 검토하고 최소 포트만 허용한다. 키 분실 시 복구 절차와 관리자 계정 권한을 문서화한다.
- 서버 시간대는 DB 저장 시 UTC와 Django `USE_TZ=True`를 적용하며, 사용자 표시 시간은 `Asia/Seoul`로 일관되게 변환한다(ERD와 일치).

## 3. 운영 설정·비밀정보

- 운영: `DEBUG=False`, 정확한 `ALLOWED_HOSTS`, 실제 HTTPS 사용 시 `CSRF_TRUSTED_ORIGINS`와 `SECURE_PROXY_SSL_HEADER`의 프록시 신뢰 범위 검토, 안전한 세션/CSRF 쿠키, HTTPS 강제 여부를 함께 확인한다. 프록시가 없으면 무작정 proxy SSL header를 설정하지 않는다.
- `python manage.py check --deploy` 통과를 목표로 하며, 항목별 보완 근거를 남긴다.
- `DJANGO_SECRET_KEY`, DB 암호, SMTP 앱 비밀번호, SSH 개인키, 배포 인증정보는 Git에 커밋하지 않는다. `.env.example`에는 빈 예시만 넣고 실제 값은 운영 서버의 제한된 권한 저장소에 둔다. GitHub Actions에는 필요한 최소 Secrets/권한만 부여한다.
- 유출 의심 시 **키 폐기 → 재발급 → 배포 재시작 → 로그 확인** 순서로 조치한다. 로그와 오류 화면에서 비밀번호·토큰·연락처가 그대로 출력되지 않도록 한다.
- 의존성 취약점 확인 및 서버/컨테이너 보안 업데이트는 실제 사용자 공개 전에 주기를 정한다.

## 4. Docker 및 데이터 영속성

- 기존 #5 기준: `web`과 `db`, `pgdata` named volume, non-root 앱 컨테이너, WhiteNoise, 개발용 override 분리.
- 앱 컨테이너 교체·재시작으로 데이터가 유실되지 않아야 한다. DB 데이터는 컨테이너 writable layer에 저장하지 않는다.
- `/healthz/`는 기본 앱 상태와 DB 연결 여부를 확인한다. 공개 엔드포인트에 내부 오류 상세·계정정보를 출력하지 않는다. 잦은 헬스체크가 DB에 불필요한 부하를 만들지 않도록 한다.
- 재시작 정책, 데이터 볼륨, Docker 로그 크기 제한, 디스크 부족 대응, CPU/메모리 사용량 확인 방법을 배포 이슈에 반영한다.
- 개발에서는 `runserver`가 가능하나 외부 운영에서는 `gunicorn` 등 운영용 앱 서버를 사용한다.

## 5. CI/CD·배포·롤백

- PR/push 시 lint/format, Django 테스트(테스트 DB), 컨테이너 이미지 빌드, `docker compose up -d --wait` 및 스모크 테스트 실행 (#6). 테스트 실패 PR은 보호 규칙 적용 이후 병합을 차단한다.
- 배포 이미지는 커밋 SHA 등 변경 불가능한 식별자로 추적한다. 운영 비밀정보는 이미지에 넣지 않는다. 실제 배포된 SHA와 배포 일시를 남긴다.
- 배포 순서(권고): 사전 백업/가용성 확인 → 변경·마이그레이션 위험 검토 → 이미지 준비 → 마이그레이션 → web 교체 → 헬스체크/스모크 테스트 → MVP 실제 동선 확인.
- **이미지 롤백과 DB 스키마 롤백은 다르다.** 파괴적 마이그레이션은 가급적 피하고, 필요 시 expand/contract 또는 복구 전략을 별도 수립한다. 백업 복원은 운영 데이터 손실 가능성이 있으므로 자동 실행하지 않는다.
- 배포 실패 시 신규 트래픽 중단 또는 이전 이미지 재배포 절차를 문서화하고, 실패 시점의 로그·원인·조치 결과를 기록한다.
- 배포 자동화는 발표 기간에는 선택 사항(#7). 검증 없이 자동 배포부터 도입하지 않는다.

## 6. DB 백업과 복구 — 신규 설계 제안

**중요:** Docker 볼륨은 영속화 수단이지 독립적인 백업이 아니다. Lightsail 인스턴스 장애와 삭제에 대비해 **서버 밖 별도 저장소**에 백업한다.

| 항목 | 초기 권고안 (아직 확정 아님) | 검증 방법 |
|---|---|---|
| 방식 | PostgreSQL 논리 백업(`pg_dump`) + 필요시 서버/볼륨 스냅샷 보완 | 백업 파일 생성·무결성 확인 |
| 주기 | 실제 사용자 운영 시 1일 1회 이상, 변경 규모에 따라 조정 | 작업 실행 기록·마지막 성공 시각 |
| 보관 | 예: 일별 7개 + 주별 4개(비용·개인정보 정책 검토 후 확정) | 만료 파일 정리 결과 |
| 위치 | 별도 권한으로 보호된 외부 저장소 | 서버 삭제 가정하에 다운로드 가능 |
| 보호 | 저장·전송 암호화, 백업 접근 최소권한, 비밀정보 분리 | 권한·암호화 설정 점검 |
| 복구 연습 | 발표 전 가짜 데이터로 1회, 실제 운영 전 정기 훈련 계획 | 분리된 임시 DB에서 복구 후 행수·핵심 흐름 확인 |
| 목표 | RPO(허용 데이터 손실 시간), RTO(허용 복구 시간) 미정 | 실제 복구 실측 후 숫자 확정 |

- 백업 파일명·기간·복구 절차는 운영 문서에 기록하되, 계정 키·비밀번호·실제 백업 데이터는 저장소에 올리지 않는다.
- 복구는 **운영 DB에 즉시 덮어쓰지 않고** 분리된 환경에서 시험한다. 실패 원인과 소요 시간 기록이 확인돼야 '복구 검증 완료'로 표시한다.
- 시연 데이터는 #24의 `seed_demo`로 재생성할 수 있지만 **실제 수강생 데이터를 대체하는 백업 수단은 아니다.**

## 7. 모니터링·로그·장애 대응 — 신규 설계 제안

- 최소 감시 항목: HTTPS 외부 응답, `/healthz/`, web/db 컨테이너 상태, CPU·메모리, 디스크/볼륨 사용량, TLS 인증서 만료, 백업 마지막 성공 시각.
- 초기에는 간단한 외부 가동 확인 및 알림 채널(메일 등)로 시작해도 된다. 도구명·주기·임계값은 예산/운영 환경을 확인한 뒤 결정한다.
- 장애 발생 시: ① 사용자 영향·발생 시각 확인 ② 로그/상태 수집 ③ 최근 배포·DB/디스크 확인 ④ 복구/롤백 결정 ⑤ 스모크 테스트 ⑥ 원인·재발 방지 기록.
- 요청 ID, 오류 종류, 발생 시각, 배포 SHA를 남기되 **비밀번호·토큰·민감 연락처 원문은 기록하지 않는다**. 로그 보관 기간·회전·접근권한을 정한다.
- 장애 수준 예시: 전체 접속 불가/데이터 손상은 긴급, 일부 기능 오류는 일반. 연락 담당자·대체 접속 경로는 실제 공개 전 확정한다.

## 8. 개인정보 및 운영 정책 — 신규 설계 제안

- 데이터 범위: 강사 계정, 수강생 이름/연락처, 미성년자 여부 및 보호자 연락처, 수업·회차 이력. 실제 정보가 들어오기 전 개인정보 처리·보관·삭제 기준 및 고지 절차를 정한다.
- 모든 조회·변경·삭제는 로그인한 강사에게 속한 데이터만 허용한다. 다른 강사의 Student·Enrollment·LessonSession·Label 접근 거부를 테스트한다.
- 관리자 계정은 필요한 최소 인원만 사용하고 MFA, 최소권한, 접근 로그를 검토한다. 데모 계정에는 실제 개인정보를 넣지 않는다.
- 가입·탈퇴, 수강생 보관, 정보 삭제 요구, 백업본의 보관 만료, 운영자 연락 경로를 서비스 공개 전 정의한다. 세부 법률 준수 여부는 국내 적용 규정에 따라 별도 검토한다.
- DB와 백업을 다루는 운영자/외부 서비스의 권한, 개인정보 사고 발견 시 대응·통지 절차도 공개 전 확정한다.

## 9. 비용·용량 계획 — 신규 설계 제안

- Lightsail 인스턴스/스토리지·스냅샷·별도 백업 저장·전송량·도메인·모니터링의 **월 예상 비용과 한도**를 합산한다. 실제 가격은 선택한 리전·사양 기준으로 산출한다.
- 계정 예산 경보를 설정하고, 디스크 증가/백업 증가/트래픽 증가를 월 1회 점검한다.
- 단일 서버에서 성능 문제나 데이터 용량 문제를 실측하기 전에는 K8s·DB 별도 서버 등 복잡한 구조를 도입하지 않는다.
