> **프로젝트 기준일:** 2026년 11월 18일  
> **GitHub:** [yeeun5364/lemit](https://github.com/yeeun5364/lemit)

## 1. 프로젝트 한 줄 소개

**LEMIT은 프리랜서 강사가 유동적인 레슨 일정과 진행 회차를 쉽고 체계적으로 관리할 수 있도록 돕는 서비스입니다.**

레슨마다 수업 시간과 장소가 다르고 휴강·보강이 발생하는 상황에서, 일정만 기록하는 일반 캘린더를 넘어 **수업 일정과 실제 진행 상태를 연결해 관리**하는 것을 목표로 합니다.

## 2. 서비스명과 방향

| 항목 | 내용 |
|---|---|
| 서비스명 | LEMIT (레밋) |
| 이름의 의미 | Lesson + Meet (브랜드용 합성 의미) |
| 서비스 지향점 | 수업의 모든 흐름을 하나로 |
| 서비스 유형 | 프리랜서 강사 중심 레슨 운영 관리 웹서비스 |
| 우선 해결 문제 | 유동적인 일정·휴강·보강 및 수업 회차 관리 |
| 개발 형태 | 개인 프로젝트, 실제 서비스로 장기 확장 지향 |

**범위 설정 원칙:** 모든 기능을 처음부터 구현하지 않는다. 서비스의 장기적인 가능성은 열어두되, 초기에는 사용자와 문제를 좁혀 핵심 기능을 완성한다.

> **브랜드 유의사항:** LEMIT/레밋과 동일하거나 유사한 이름을 사용하는 국내외 사례가 확인되었다. 정식 출시 전 상표 및 도메인 사용 가능 여부를 별도 확인해야 한다. 프로젝트명은 **LEMIT으로 결정**했다.

## 3. 해결하려는 문제

프리랜서 강사나 개인 클래스 운영자는 수업을 직접 조율하고 관리해야 하는 경우가 많다.

- 수강생마다 레슨 요일·시간이 다르다.
- 정기 레슨과 비정기 수업이 섞여 있다.
- 개인 사정에 따른 휴강·보강·시간 변경이 생긴다.
- 수업을 몇 회 진행했고 몇 회가 남았는지 확인해야 한다.
- 여러 레슨실 또는 기관에서 수업할 경우 장소별 일정을 함께 관리해야 한다.
- 일정과 수업일지·진도 기록이 따로 분리되기 쉽다.

기관이나 방과후 수업 역시 일정 변경이 발생하지만, 비교적 고정된 시간표로 운영되는 경우가 많다는 점에서 **일정의 유동성이 높은 개인 레슨과 프리랜서 운영**을 우선 대상으로 설정했다.

## 4. 핵심 사용자

### 1차 사용자 — 개인 레슨을 운영하는 프리랜서 강사

- 악기·음악·미술·체육 등 분야에 제한을 두지 않는다.
- 학생별로 다른 일정과 레슨 횟수를 직접 관리한다.
- 강사가 스스로 학생, 수업, 장소, 완료 여부를 등록한다.

### 2차 사용자 — 출강 강사 및 원데이 클래스 운영자 (확장)

- 여러 장소에서 수업하는 강사
- 특정 날짜에 소규모 체험·공방 수업을 운영하는 사람
- 예약 인원, 정원, 취소 등은 추후 필요에 따라 설계한다.

### 장기 사용자 — 학생 및 학부모

- 수업 일정, 기록, 공지 등을 확인하는 역할로 확장 가능하다.
- 초기 MVP에서는 강사 중심으로 시작한다.

**제외할 역할:** 별도의 기관 관리자 전용 계정이나 기관 전체 관리 시스템은 현재 범위에 넣지 않는다. 다만 강사가 등록하는 **기관명과 수업 장소 정보는 필요**하다.

## 6. 2026년 11월 24일 발표용 MVP

**발표 일정:** 2026년 11월 24일(화) 오후 3시 · 약 5분 발표 및 짧은 질의응답

### 목표 사용자 흐름

1. 강사가 수강생을 등록한다.
2. 수강생의 레슨 일정을 등록한다.
3. 등록된 일정을 조회한다.
4. 수강생이 보낸 메시지를 메시지함에서 확인한다. 직접 학습시킨 ML 모델이 휴강 요청·보강 요청·일정 변경·일반 메시지로 분류해 보여준다 (UC-17, 시연에서는 가상 수강생 메시지).
5. 실제 수업이 끝나면 완료 처리한다.
6. 진행한 수업과 남은 레슨 횟수를 확인한다.

발표까지 시간이 제한되어 있으므로 이 핵심 흐름이 **실제로 동작하는 웹서비스**가 되도록 우선한다. 가능하다면 특정 수업의 휴강·보강 처리를 시연하는 것이 다음 목표다.

### 범위에서 우선 제외할 것

- 원데이 클래스의 예약·결제 전체 흐름
- 학부모 및 학생용 별도 화면 (수강생 메시지는 MVP에서 강사가 시연용으로 대신 등록)
- 실제 이메일·문자로 메시지 보내기, 새 메시지 알림
- 문자·푸시 발송
- AI 기반 진도·수업 추천, 외부 AI API 연동, 예측 결과로 일정을 자동 변경하는 기능
- 기관 관리자용 기능
- 복잡한 정산 및 회원권 판매

> **과제 조건 변경 (2026-11-19):** 직접 학습시킨 ML/DL 모델이 웹서비스와 연결되어 실제로 추론해야 한다. 2026-11-18의 "AI 없이 진행" 확인을 대체한다. 기존 MVP 흐름과 설계는 유지하고, 수강생 메시지 AI 분류(UC-17)를 추가한다. 설계·결과·한계는 [ML.md](ML.md).

## 7. 기술 구성 및 선택 이유 (현재 설계안)

| 영역 | 기술 | 채택 이유 / 비고 |
|---|---|---|
| 개발 언어 | Python | Django 및 데이터 처리 생태계 활용 |
| 백엔드 | Django | 인증, 관리자 기능, 데이터 중심 웹서비스 구현에 적합 |
| 프런트엔드 | Django Templates + HTML/CSS (+필요시 JS) | 개인 개발 초기의 화면 및 배포 복잡도 최소화 |
| 데이터베이스 | PostgreSQL | 강사·수강생·수업·회차 간 관계와 데이터 일관성 관리 |
| 아키텍처 | Monolith | 한 사람이 개발·테스트·배포하기 쉬운 구조 |
| 컨테이너 | Docker | 개발 및 배포 환경 일관성 |
| CI/CD | GitHub Actions | 변경 시 테스트·배포 자동화 |
| 배포 | AWS Lightsail | 비교적 단순한 초기 클라우드 서버 구성 |
| API | Django REST Framework, drf-spectacular | 2026-11-25 채택(#102, 발표 피드백 후속 #110). 외부 API에 필요한 권한·입력 검증·오류 형식 통일·페이지네이션·요청 제한·OpenAPI 문서를 검증된 형태로 쓰고, 업무 규칙은 기존 `services.py`·`classifier.py`를 호출해 웹과 같은 규칙을 공유. 순수 Django는 이 기능들을 다시 만들어야 하고, Django Ninja는 자료가 적어 제외. 인증은 강사별 API 키(범위: 읽기·일정 변경·메시지 발송, 만료 필수), 세부 명세는 #102 |
| 메일 발송 | Gmail SMTP (앱 비밀번호) | 비밀번호 재설정 메일용. Django 기본 기능이라 구현이 간단하고, 자체 도메인 없이도 스팸 분류 위험이 낮음. 초기엔 개발자 개인 계정, 이후 서비스 전용 계정으로 교체(`.env`만 변경) |
| 파일 저장 | 객체 스토리지 | 사진·첨부파일 기능이 필요해질 때 검토 |
| AI/ML | scikit-learn (TF-IDF + Logistic Regression), joblib | 과제 조건(2026-11-19). 수강생 메시지 분류. 데이터가 수백 건이라 단순 선형 모델이 적합하고 CPU만으로 분류 1건 약 1.0~1.6ms(운영 서버 측정, 모델 캐시 사용, [ML.md](ML.md) §6). Django 안에서 직접 추론해 별도 서버·GPU 없음. 학습은 개발 PC, 서버는 검증된 모델 파일만 사용 ([ML.md](ML.md)) |
| 캐시 | AI 모델만 메모리 캐시 (프로세스당 1회 로드) | 2026-11-20 결정(#51). 모델은 배포 때만 바뀌어 오래된 값 문제가 없고, 운영 서버 측정에서 분류 1건이 10.2~27.4ms → 1.0~1.6ms(약 10~17배, 3회). 수업·회차·메시지 데이터와 `/healthz/`는 캐시하지 않음: 화면이 강사마다 달라 재사용이 적고, 회차·요청은 최신이어야 하며, 측정상 느린 곳이 없음. Redis 등 별도 캐시 서버는 2GB 서버에 장애 지점만 늘려 도입하지 않음. 사용자 증가로 느려짐이 **측정되면** 다시 검토. 정적 파일은 WhiteNoise 기본(브라우저 60초, 압축). **추가(2026-11-25, #102):** API 요청 제한 횟수만 Django DB 캐시(`DatabaseCache`)에 저장. 프로세스별 메모리 캐시는 gunicorn worker마다 횟수를 따로 세기 때문이며, 새 캐시 서버 없이 기존 PostgreSQL로 공유. 화면 데이터는 여전히 캐시하지 않음 |

**기술 선택 원칙:** 수업에서 배운 기술을 모두 넣는 것이 목적이 아니라, 필요한 기능에 적합한지 근거를 설명할 수 있어야 한다.

### 개념 아키텍처

```text
[강사 웹 브라우저]
        |
        v
[Django 모놀리스 애플리케이션]
  - 사용자/인증
  - 수강생 관리
  - 레슨/일정 관리
  - 수업 회차/기록 관리
  - 메시지함 + 메시지 분류 추론 (모델 파일 포함)
        |
        v
   [PostgreSQL]

학습(개발 PC): ml/train.py → 검증된 모델 파일 커밋 → CI에서 ml.verify

실행/배포: Docker + AWS Lightsail
자동화: GitHub Actions → 테스트 → 빌드 → 배포
```

현재는 **제안 구조**이며 실제 서버·DB·CI/CD 구성이 완료되었다는 의미는 아니다.

## 11. 발표 때 강조할 내용

- **왜 만들었는가:** 유동적인 레슨 일정과 실제 진행 회차를 함께 관리하는 어려움
- **누구를 위한가:** 개인 레슨을 운영하는 프리랜서 강사
- **무엇을 해결하는가:** 수강생별 수업 일정을 한눈에 보고 수업 완료 및 잔여 횟수를 추적, 수강생 메시지 중 휴강·보강·일정 변경 요청을 바로 골라 봄
- **ML은 어떻게 만들었는가:** 합성 데이터 구성, Pipeline으로 누수 없는 학습·평가, 미리 정한 성능 기준, 모델 파일 검증(CI), 실패해도 서비스가 멈추지 않는 구조, 한계
- **왜 이렇게 만들었는가:** Django 모놀리스, PostgreSQL, Docker, GitHub Actions, Lightsail의 선택 근거
- **어디까지 구현했는가:** 발표 시점에 실제 완료·검증한 기능만 표시
- **다음 단계는 무엇인가:** 휴강·보강, 기록, 학생·학부모 소통, 원데이 클래스 확장
