## 결정 사항
- 진행 순서: #102 API 공통 설계 → #101 분류 모델 API → #103·#104·#105 조회 API → (사이사이 #111·#100) → #106·#107 변경·발송 API → #108 문서·운영 검증 → #109 MCP. 이후 #99→#98, #83→#81, #19·#21, #89·#90
  - 이유: #102가 API 이슈 8개의 선행 조건이고, 읽기·추론처럼 데이터를 바꾸지 않는 API부터 공통 설계를 검증하기 위해
- API 사용 대상: 강사 본인의 AI 에이전트·MCP 연동과 학습용 데모를 우선 고려 (외부 개발자·타 서비스는 우선 대상 아님)
- API 프레임워크는 Django REST Framework(DRF): 권한·입력 검증·일관된 오류·페이지네이션·요청 제한·OpenAPI 문서(drf-spectacular)를 검증된 형태로 쓰고, 비즈니스 로직은 기존 `services.py`·`classifier.py`를 재사용해 웹과 API가 같은 규칙을 공유하기 위해 (순수 Django는 이 기능들을 다시 만들어야 하고, Django Ninja는 자료가 적음)
- 인증은 강사별 API 키로 시작하되 키에 소유 강사·범위(읽기/쓰기)·이름표·만료를 담아, 이후 외부 서비스가 요청하고 강사가 승인하는 OAuth 방식(원격 MCP와 연결)을 덧붙일 수 있게 함. OAuth 도입 여부는 #109에서 판단
- API 공통 형식(#102)
  - 버전: URL 경로 `/api/v1/` (로그·curl에서 바로 보여 디버깅이 쉬움). 필드 추가는 v1 안에서, 기존 사용자를 깨는 변경(삭제·이름·의미 변경)일 때만 v2
  - 성공 응답: DRF 기본 형태(단건은 객체, 목록은 `count/next/previous/results`), 감싸는 봉투 없음
  - 오류 응답: 모든 오류를 `{"error": {code, message, hint, fields[], retryable, retry_after?, docs, request_id}}` 한 형식으로. 무엇·어디·왜·어떻게 고치는지·재시도 가능 여부는 자세히, 다른 강사 데이터 존재·서버 내부·메시지 본문·키 값은 알리지 않음. `/api/` 아래 404·500도 JSON
  - 다른 강사의 데이터는 403이 아닌 404 (존재 여부를 드러내지 않음). 403은 키 범위 부족에만 사용
  - 시간은 `+09:00`을 명시한 ISO 8601, 날짜 조건은 서울 날짜 기준 `YYYY-MM-DD`, 필드는 snake_case, 상태는 영문 코드 + `status_display`
- API 키(#102)
  - 강사만 웹 '설정 > API 키'에서 발급(API 키로 키 생성 불가), 발급 시 비밀번호 재확인, 강사당 유효 키 5개
  - `lemit_` 접두사 + 무작위 값, 원문은 발급 직후 한 번만 표시, DB에는 SHA-256 해시만 저장(무작위 긴 키라 느린 해시 불필요), `Authorization: Bearer`만 허용, API는 세션 인증 미허용
  - 범위 3단계: 읽기 / 일정 변경 / 메시지 발송 (발송은 수강생에게 전달되어 되돌릴 수 없으므로 분리)
  - 만료 필수: 30일·90일(기본)·180일·1년, 만료 전에는 비밀번호 확인으로 같은 키 값 그대로 연장, 14일 전부터 '곧 만료' 표시, 만료 후에는 새로 발급. 만료 없는 키(Stripe 방식)·재발급만(GitHub 방식)과 비교해 선택. 자동 갱신이 필요해지면 OAuth(#109)로 해결
  - 마지막 사용 시각은 1분에 한 번만 갱신, 요청 제한은 DB 캐시(`DatabaseCache`)로 worker 간 공유
